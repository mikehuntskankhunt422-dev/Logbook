# Milestone 2: Book builder and print PDFs

Status: **proposed 2026-10-07**, waiting for your OK · Expands [PLAN.md](PLAN.md) §1.4 and §3 (M2) · Author: Claude

## 0. In one paragraph

M2 turns journal entries into a book. You pick entries and a product, flip through a preview with a page count and warnings, and the server renders an interior PDF and a wraparound cover PDF that Lulu accepts. **Done means** the 40-page and 200-page sample books pass Lulu sandbox `/validate-interior/` and `/validate-cover/`, and every golden check (page sizes, page count, fonts, transparency) passes in CI. No prices, payments or orders yet; those are M3 and M4.

## 1. What I tested before writing this

A throwaway spike (2026-10-07, Chromium 141 via Playwright): a 50-page test book with mirrored margins, running heads, page numbers, a contents page, a gradient, colour emoji and a transparent PNG, rendered with and without Paged.js and inspected with `pdfinfo` and `pdffonts`.

| Finding | What it means for M2 |
|---|---|
| Paged.js has had **no stable release since 0.4.3 (July 2023)**; the last beta is 0.5.0-beta.2 (October 2024). PLAN risk #3 has happened | Pin 0.4.3 exactly and treat it as our code (D34) |
| Paged.js 0.4.3 **still works** in current Chromium: 50 pages in about 1.8 s. `bleed: 0.125in` gives 450 × 666 pt pages (6.25 × 9.25″, as Lulu wants). Running heads (`string-set`), page numbers in margin boxes and `:left`/`:right` mirrored margins all print. `target-counter()` contents numbers matched the real pages (4, 6, 8) | The engine choice (D9) holds |
| `leader()` is not supported and silently voids the whole `content` rule | Dot leaders via CSS layout; a unit test rejects `leader(` in print CSS |
| Native Chromium printing (no Paged.js) laid the same content out in **53 pages instead of 50**, and ignores `bleed` | Preview and server must run the same engine, as D9 says |
| **Variable fonts embed as Type 3** (Newsreader and Bricolage both). The same fonts as static files embed as CID TrueType | Print uses static font files (D35) |
| **Colour emoji embed as Type 3 bitmaps with soft masks** (`/SMask` = transparency); a PNG with alpha does too. Without both: zero soft masks | Emoji become vector SVGs or a monochrome font (D36); images are flattened on the server (D37) |
| CSS `linear-gradient` produced no transparency | Gradient covers are safe to print |

A second render after slice A (the real `packages/core` print output: 40 entries, every block type, 92 pages) settled in 2 layout passes. Contents page numbers matched the real pages, front pages carried no running heads, and the PDF had only CID TrueType fonts, no soft masks, no alpha and no link annotations. It also found three things slice B must handle:

| Finding | What it means for M2 |
|---|---|
| Paged.js re-fetches every stylesheet with XHR, which fails from `file://` | The renderer serves the book from one routed local origin; everything else is blocked (D41) |
| Chromium rounds page sizes up to 1/300″: a 918.8 pt cover came out 918.96 pt. Interior sizes are exact multiples, so they're unaffected | After rendering, set the cover's MediaBox, TrimBox and BleedBox to Lulu's exact numbers |
| Node's built-in type stripping can't run `packages/core` (it uses constructor parameter properties) | The server runs with `--experimental-transform-types` or a build step |

## 2. Changes to the approved plan (need your OK)

1. **Lulu sandbox moves into M2** (was "before M3/M4"). `/cover-dimensions/` and `/validate-*` are M2 acceptance criteria.
2. **A public file URL moves into M2.** Lulu's validators fetch PDFs by URL, so the samples must be hosted somewhere Lulu can download. I'd bring Cloudflare R2 forward from M4; M3 needs it anyway, because proofs are rendered before checkout. Fallback for the two samples only (no personal content): a GitHub Release asset URL. That's unverified with Lulu.
3. **`scripts/verify-lulu-packages` moves from M4 to M2.** Covers need confirmed package IDs and dimensions.
4. **The upload boundary.** M2 defines the print bundle format. The "Prepare my book" consent dialog plus presigned upload lands in M2 if R2 is ready; otherwise it's the first item of M3. Until then the render server runs only locally and in CI. Nothing deployed accepts journal content before presigned uploads exist (PLAN §6).

New decisions D34–D41 are recorded in [DECISIONS.md](DECISIONS.md).

## 3. The book (defaults)

| Part | What | Option |
|---|---|---|
| Title page | Title, subtitle, author, date range | — |
| Colophon | "Made with Logbook", printed by Lulu, emoji credit (D36), print date | — |
| Contents | Months → entries with page numbers | on by default |
| Month dividers | Month and year, on a right-hand page | on by default |
| Entries | Opener with date, title, mood, tags, gradient band or cover photo; then the blocks. Each entry starts on a new page | "flow continuously" saves pages |
| Notes pages | Appended to reach an even count and the product minimum (32 paperback / 24 hardcover) | — |
| Running heads / folios | Month + year on the outer top corner; page number at the foot | — |

Block fallbacks follow PLAN §1.4. Two details settled here:

- **YouTube/Vimeo embeds** get a fixed-size box. The server fetches the thumbnail at render time; if that fails, it prints a title card. The preview shows a title card in the same box, so layout is identical.
- **Audio** waveforms are computed on the device (`OfflineAudioContext`) and travel in the bundle as peaks. If decoding fails, the card shows no waveform.

## 4. Work, in order

Slices A–C need no credentials, so I can start immediately; D and E wait on the items in §7.

### A. Print layout in `packages/core/src/print/` (DOM-free; runs in browser and Node)

- `products.ts`: the 16 dotted package IDs (PLAN §4), trim, 0.125″ bleed, 0.5″ safety, page limits per binding.
- `planner.ts`: gutter bands (L3 p.9, D22); the gutter ↔ page-count loop (≤ 3 passes, larger gutter on oscillation); even + minimum via Notes pages; above 800 pages, a "split into volumes" suggestion with date boundaries.
- `selection.ts`: `BookOptions` zod schema (date range or hand-picked ids, title, subtitle, author, product, cover, toggles), resolved to dated entries, trash excluded.
- `richtext-html.ts` (D41), `blocks-html.ts`, `book-html.ts`, `print-css.ts`: one HTML document + one print stylesheet, transparency-free (no `opacity`, `rgba`, shadows, filters, blend modes; a unit test scans the CSS).
- `qr.ts`: vector SVG QR codes (uqr, zero dependencies).
- `resolution.ts`: placed size per block and layout → effective PPI; warnings below 300 PPI, by filename.
- `cover.ts`: wraparound geometry from Lulu's dimensions (spine = width − 2 × trim − 2 × bleed), spine text off at ≤ 80 pages (D23). The guide's formulas are used only as a test cross-check.
- `bundle.ts`: the print bundle (options, product, entries, media list with SHA-256 and sizes, audio peaks), zod-validated: the contract between client and server.

### B. Renderer, samples and golden tests (`apps/server`, first part)

- Fastify 5 + TypeScript scaffold; config with the `APP_MODE` guard (D18); pino with the redaction list and the "no content fields in logs" test from day one (PLAN §6).
- Renderer: Playwright Chromium with pinned Paged.js (D34), static fonts (D35), request allowlist (D41), `page.pdf({ preferCSSPageSize: true })`. The cover is one page at Lulu's exact size and needs no Paged.js.
- Image pipeline with sharp (D37), including greyscale conversion for B&W interiors (no CSS filters).
- `scripts/make-samples`: deterministic 40-page and 200-page journals that use every block type, plus a low-resolution photo, a transparent PNG, emoji, long words and lists. Output PDFs are CI artifacts, not committed (they'd bloat git).
- Golden tests and a new CI job, `print`, that renders the samples and uploads the PDFs so you can look at them.
- `POST /api/render` exists in test mode on localhost only, until slice E puts it behind uploads.

### C. Builder UI (`apps/web`)

- Route `#/book` with steps **Entries → Product → Cover → Options → Preview**. Last-used settings are kept (D40).
- Preview: Paged.js inside an isolated `srcdoc` iframe (it rewrites the document and injects global styles), re-run on demand with progress and cancel. Spreads on desktop, single pages on phones; keyboard and reduced-motion friendly.
- Layout depends only on media metadata (width and height), never on loaded pixels. The preview can therefore use small thumbnails and still match the server's page count (D37).
- Warnings panel: low-resolution images by filename with a link to their entry, padding notice ("+3 Notes pages to reach 32"), the 800-page split suggestion, and what prints differently (video → poster frame, etc.).
- Cover preview gets its dimensions from the server, or from a labelled approximation when offline (D39).
- Page count shown as "estimate until proof"; the price arrives in M3.
- e2e (Playwright): build a book from a seeded journal, preview page count vs. server, offline preview, axe checks.

### D. Lulu sandbox (needs your sandbox credentials and network access)

- Lulu client: OAuth token with cache (answers open question #1, the sandbox token URL), `/cover-dimensions/` with a per-(package, pages) cache, `/validate-interior/` and `/validate-cover/` with polling.
- `scripts/verify-lulu-packages`: checks all 16 IDs and records cover dimensions. The hardcover check answers open question #7 (case-wrap wrap and hinge areas).
- `scripts/validate-samples`: hosts the sample PDFs, validates them, and writes a dated report into ASSUMPTIONS.md.
- First thing when credentials arrive: validate the spike PDF, so any Lulu objection to Chromium output surfaces before the layout work is finished.

### E. Consent and upload (needs R2)

- "Prepare my book" dialog (PLAN §1.5 step 2): N entries, M photos, total size, where it goes, when it's deleted.
- Client builds the bundle, downscales media to print resolution, uploads with presigned PUT; the server renders from R2. If R2 isn't ready, this opens M3.

## 6. Risks specific to M2

| Risk | Mitigation |
|---|---|
| A future Chromium breaks Paged.js | The server pins Playwright and its Chromium; golden tests run on every PR. Users' browsers may drift, but that affects only the preview: the customer approves the server PDF (D9). Last resort: native Chromium on the server plus our own block packer (PLAN risk #3) |
| Lulu objects to something the spike didn't cover (PDF version, RGB, Type 0 fonts) | Validate the spike PDF on day one of slice D. Fallback: Ghostscript flattening pass (PLAN risk #2) |
| Big books are slow or memory-hungry in a phone browser | Thumbnails in preview (layout ignores pixels), on-demand re-render with cancel, progress shown. Measured in slice C |
| Chromium updates change page counts | Goldens are tied to the pinned Playwright version; the server's Docker image uses the same version |
