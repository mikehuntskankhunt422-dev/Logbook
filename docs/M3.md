## 0. In one paragraph

M3 puts a price on a book and takes payment for it. The builder shows a price estimate from Lulu's live costs. "Prepare my book" uploads the chosen entries (with consent) so the server can render and validate the real print files. The customer then sees the proof and the final price with shipping, and pays on Stripe's hosted Checkout. Stripe's webhooks are the source of truth for "paid". **Done means** the pricing unit tests pass (minimum, maximum, hardcover, B&W, margin floor, never below cost), webhook handling is tested with Stripe-signed fixtures, and in Stripe **test mode** the cards `4242 4242 4242 4242` (paid), `4000 0000 0000 0002` (declined) and `4000 0027 6000 3184` (3-D Secure) each end in the right order state. Creating the Lulu print job is M4.

### C. Consent and upload (done, verified on B2 with the Lulu sandbox)

Any S3-compatible bucket works (D54). Lulu validation of real orders then runs automatically, because Lulu can fetch the presigned URLs; with the local backend it's skipped and the proof says so.

**Verified end to end, 2026-10-07**, on a private Backblaze B2 test bucket (region `us-east-005`) with the Lulu sandbox:

1. `npm run storage:setup -w @logbook/server` first failed: B2 refused the lifecycle rules (`MalformedXML`: "orders/ has an Expiration rule but there is no ExpiredObjectDeleteMarker rule with the exact same prefix"). B2 wants each expiry rule paired with a second rule, with the same prefix, that removes delete markers. The store now sends that pair to B2 (only to B2), and B2 returns both rules as set. Setup then passed: CORS for `http://localhost:5173` and `:4173` (`vite preview`, where the e2e tests run), 7-day deletion of `orders/`, a browser-style preflight, and an upload and a download through signed links.
2. `LOGBOOK_E2E_ONLINE=1 npx playwright test e2e/prepare.spec.ts --project=desktop-chromium` in `apps/web` (production build, real API with the `S3_*` and `LULU_SANDBOX_*` variables) **passed in 24 s**. The order went from created to `quoted` in 16 s:
   - The browser sent the manifest to `POST /api/orders` and PUT both files (`bundle.json`, 1,249 bytes; the picture, 156 bytes) straight to `s3.us-east-005.backblazeb2.com`, then `POST …/submit`. Nothing went through `/api/local-storage/`.
   - The server checked both hashes, rendered 32 pages with the cover sized from Lulu's `/cover-dimensions/` (not approximated), stored `print/interior.pdf` (49,794 bytes) and `print/cover.pdf` (41,969 bytes) in the bucket and deleted the uploaded sources (only the two PDFs are left under the order's prefix).
   - The Lulu sandbox fetched both PDFs through presigned GET links: interior validation 1016697 `NORMALIZED`, 32 pages; cover validation 1016696 `NORMALIZED`; no errors.
   - Priced from Lulu's live cost: 6 × 9 in premium colour paperback, matte, 32 pages, **$24.99** (the minimum, as in §2). The page said "The printer has checked both files and accepted them." and "The book costs $24.99 plus shipping and any tax.", and both proof links (signed B2 URLs) returned PDFs.
3. The e2e config now blanks the `S3_*` and `R2_*` variables unless `LOGBOOK_E2E_ONLINE` is set. Before, an environment with a bucket configured (like this one) would have sent the normal e2e run's uploads to the real bucket, because a bucket takes precedence over `LOCAL_STORAGE`. The default run stays on local storage with no Lulu, and the online test is skipped unless it's asked for.

To repeat it: set the `S3_*` (or `R2_*`) and `LULU_SANDBOX_*` variables, run `storage:setup` once, `npm run build`, then the command in step 2 (in a container whose Chromium differs from Playwright's build, add `LOGBOOK_CHROMIUM_PATH`).

**Backblaze B2 (free, no card):**
1. Sign up at backblaze.com for B2 Cloud Storage and pick a region.
2. Buckets → Create a Bucket: a unique name (e.g. `logbook-orders-<something>`), Private.
3. Application Keys → Add a New Application Key: access to all buckets, Read and Write. Keep the keyID and applicationKey (shown once).
4. In this environment's settings: `S3_ENDPOINT` (the bucket's "Endpoint", e.g. `s3.us-west-004.backblazeb2.com`), `S3_BUCKET`, `S3_ACCESS_KEY_ID` (keyID), `S3_SECRET_ACCESS_KEY` (applicationKey); allow `*.backblazeb2.com` under Network access.
5. Run `npm run storage:setup -w @logbook/server`: it sets CORS and the 7-day deletion and checks them.

**Cloudflare R2:** the same, with `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` and `*.r2.cloudflarestorage.com` (needs a payment card on the Cloudflare account).

### E. Stripe (needs D and keys)

- Config: `STRIPE_TEST_SECRET_KEY` (must start `sk_test_`) and `STRIPE_TEST_WEBHOOK_SECRET` in test mode, live equivalents only with `APP_MODE=live` + `ALLOW_LIVE=true`; startup refuses any mix (D18).
- Checkout Session from the stored quote, never from client numbers: USD line items, `allowed_countries` = the chosen destination, up to 3 shipping options, phone collection, `automatic_tax` when `STRIPE_TAX_ENABLED=true`, `metadata.order_id`, `client_reference_id`, idempotency key `checkout:<orderId>:<quoteVersion>` → `awaiting_payment`.
- Webhooks: raw-body signature check, event IDs stored and processed once, `checkout.session.completed` / `async_payment_succeeded` → `paid` only when `payment_status` is `paid`; `async_payment_failed` and `expired` handled.
- Tests: Stripe-signed fixtures (the `stripe` package's test header helper) for every event; test-mode runs with the three cards through `stripe listen --forward-to`.

## 5. Risks specific to M3

| Risk | Mitigation |
|---|---|
| Lulu's costs move between quote and checkout | Quotes are stored with a version; checkout re-quotes if the stored quote is older than a day, and the customer sees any change before paying |
| Shipping re-quote with the full address after payment exceeds the buffer | $1 buffer plus the 50¢ rounding; overshoot is absorbed and logged (PLAN §7) |
| Lulu taxes our purchase in some US states | The price uses Lulu's cost excluding tax; the order record keeps Lulu's tax so the margin report shows it; a resale certificate is the fix (PLAN §8) |
| Someone uses the open order endpoint to fill our storage | 10 new orders per address per hour, 50 MB per file and 5 GB per order, upload links valid for an hour, files deleted after 7 days. Behind Fly's proxy, Fastify's `trustProxy` must be on so the address is the client's (deployment, M6) |
