## 0. In one paragraph

M5 puts Logbook on the desktop. The Tauri 2 app shows the same web app, but the journal lives as ordinary files in a folder you choose, which can sit inside OneDrive, Dropbox or iCloud Drive. Logbook notices when a sync service changes files underneath it, and when two computers changed the same entry, it shows both versions side by side for you to choose. A web journal moves to desktop through its backup zip. Installers are built for Windows (MSI and NSIS), macOS (dmg) and Linux (AppImage, deb, rpm) by a GitHub Actions matrix that attaches them to a release, and the app updates itself from signed releases. **Done means**: the filesystem store passes the same contract tests as IndexedDB plus its own layout, watcher and conflict tests; a web backup restores into a desktop folder; Linux installers are built here and the app starts from them; the workflow builds all three platforms; an update signed with the updater key is accepted and a tampered one refused; and each OS has written signing instructions. Installers stay unsigned until you've chosen signing routes (§6).

## 1. What I checked before building (2026-10-09)

Full table with sources in [ASSUMPTIONS.md](ASSUMPTIONS.md), "Desktop (Tauri 2)". Tauri's, Microsoft's and the certificate sellers' websites aren't reachable from the build environment, so I read the repositories those websites are built from, and the plugin crates' own code. In short:

- **Versions.** Tauri 2 is current (3 is in alpha). Pinned to the newest releases at least two weeks old (D77): CLI 2.11.5, `tauri` 2.11.6 with `@tauri-apps/api` 2.11.1, dialog 2.7.3, fs 2.5.2, updater 2.12.0, process 2.3.1.
- **Updater.** Signed with a minisign key pair from `tauri signer generate`; the private key comes from `TAURI_SIGNING_PRIVATE_KEY` at build time, and losing it means installed apps can't be updated again. `latest.json` carries the *content* of each `.sig`. The plugin looks for `{os}-{arch}-{installer}` before `{os}-{arch}` (source only, not in the docs). It checks the signature before installing, and can require the signature to name the same version as `latest.json`, which stops an old signed release being replayed as new.
- **File access.** The fs plugin accepts a path that the app's runtime scope allows, so Rust can grant exactly the folder you picked, with nothing in the static configuration. On Linux and macOS a recursive grant doesn't cover dot-folders.
- **Building.** AppImages must be built on the oldest Linux they should run on (Ubuntu 22.04). MSIs only build on Windows. Unsigned macOS builds should be ad-hoc signed so Apple Silicon doesn't call them "damaged".
- **Signing.**
  - *Windows:* unsigned installers get SmartScreen's "Windows protected your PC" with "Run anyway". OV and EV certificates both still warn until reputation builds. **Azure Artifact Signing is open to Australian organisations but not individuals** (individuals: US and Canada only), and an organisation needs a website and an email on its own domain. That answers open question #11. The Microsoft Store route still needs a signed installer.
  - *macOS:* Apple Developer Program, US$99 a year, open to individuals and sole traders; Developer ID certificate plus notarisation.
  - *Linux:* nothing needs signing to run.
- **Couldn't check from here:** individual OV certificate prices (Certum, SSL.com), Artifact Signing's exact price, whether Microsoft treats an Australian sole trader as an organisation, the Microsoft Store fee, and how OneDrive, Dropbox and iCloud name their conflict copies (the design doesn't depend on the names, §2.3).

## 2. Design

### 2.1 The shell (slice A)

- `apps/desktop` holds only the Tauri side: `src-tauri/` (Rust, `tauri.conf.json`, capabilities, icons) and the CLI. The window loads the **same web app**, built with `vite build --mode desktop` into `apps/web/dist-desktop` (D78):
  - no service worker or PWA manifest (the app updates through the updater, §2.6);
  - Tauri packages load only in desktop builds, so the website's bundle doesn't change.
- Window: "Logbook", resizable, with `dragDropEnabled: false` so the editor's own drag-and-drop of photos keeps working (Tauri would otherwise take file drops itself).
- Capabilities grant only what the app uses: the Logbook folder commands (§2.2), the fs plugin's read, write, rename, remove, mkdir, stat, exists and watch with **no static scope**, the dialog plugin's save and open, the updater and relaunch.
- Ordering from the desktop needs the hosted API (M6): the builder and preview work offline with estimates, and "Prepare my book" says the print service isn't available, as the website does without an API (D85).

### 2.2 The folder and its layout (slice B)

**Choosing the folder** is done in Rust (D79): a native folder dialog; the choice is remembered in the app's config folder and granted to the fs plugin at each start. The web page can't grant itself any other folder. If the chosen folder holds a journal (`logbook.json`) or is empty, it's used as is. Otherwise Logbook makes a `Logbook` folder inside it, so picking "Documents" doesn't fill Documents with journal files.

**Layout** = the backup zip's layout (PLAN §1.2, D7), so a folder and a backup of it list the same files:

```
Logbook/
  logbook.json                                    format, version, and the passcode vault when one is set
  entries/2026/2026-10-07--a-good-day--k3f9x2m4n5p6.json
  trash/2026/2026-09-01--old--a8d2kqzz7w4c.json   deleted entries (30 days, as on the web)
  media/k3/k3f9x2m4n5p6.meta.json                 picture, video and file details
  media/k3/k3f9x2m4n5p6.jpg                       the original file, named by id and type
  entries/<id>.json.enc, media/<xx>/<id>.meta.json.enc, media/<xx>/<id>.bin.enc   with a passcode
```

- **What lives elsewhere** (D80). `logbook.json` changes only when the passcode does. Device preferences (theme, backup reminder counters), the book draft and print-order tokens stay on the device (the app's own storage), as they're per-device. Otherwise every save would rewrite a shared file and two computers syncing the folder would make conflict copies of it all day. There is no `.logbook/` folder in M5: the search index is rebuilt in memory (D8's cache isn't needed yet).
- **Writes are atomic** (D81): to a temporary file next to the target, then renamed over it, so a sync client or a crash never sees half a file. Changing an entry's title or date, or deleting it, writes the new name first and then removes the old. Files Logbook doesn't recognise are never touched.
- **`packages/storage-fs`** implements the `RecordStore` interface (D28) over a small filesystem interface with two implementations: Node's `fs` (tests, scripts) and Tauri (the app). Listing the folder and reading many small files go through two Rust commands confined to the chosen folder, one call each instead of one per file. Single files, writes and watching go through the fs plugin.

### 2.3 Changes from outside, and conflicts (slice C)

- **Watching** (D83): the fs plugin's recursive watcher, debounced, plus a rescan whenever the window regains focus. A rescan lists the folder in one call and reads only files whose size or time changed. A file whose content equals what Logbook last wrote is its own write and is ignored. Views refresh when entries or media really changed. If `logbook.json`'s passcode vault changed (a passcode set on another computer), the app asks to reopen the journal.
- **Conflicts are found by content, not file names** (D82): every entry file carries its id, so two files with the same id are two versions of one entry, whatever the sync service called the copy (`… (1).json`, `… (conflicted copy).json`, `…-DESKTOP-PC.json`), and also when both computers renamed it. The app uses the correctly named file, or else the newest. A banner says "N entries were changed on two computers". The conflict view shows the versions side by side (date, title, when changed, words, photos, the start of the text, decrypted when a passcode is on), with **Keep this one** on each and **Keep both** (the other becomes a separate entry). Nothing is deleted until you choose.
- **Media garbage collection waits 7 days on the desktop** (D84): a sync service can deliver a new photo before the entry that uses it, and collecting it in between would delete it on every computer.

### 2.4 Import from a zip backup (slice D)

The first-run screen offers "Choose a folder for your journal" and "Start from a backup (.zip)", which restores a web or desktop backup into the chosen folder through the same `importBackup` the website uses (checksums, passcode, merge or replace). Settings keeps "Restore from backup" and "Download backup". On the desktop a backup is saved through the system's save dialog, because WebView downloads behave differently on each OS.

### 2.5 Installers and releases (slice E)

- Linux, built here: AppImage, deb and rpm, then checked: package metadata, the deb installed in this container, and the app started from the AppImage under a virtual display.
- `.github/workflows/desktop.yml` (D86):
  - **Builds** Linux (Ubuntu 22.04: AppImage, deb, rpm), Windows (MSI, NSIS) and macOS (one universal dmg for Apple Silicon and Intel) whenever desktop code changes, and keeps the installers as workflow artifacts.
  - **Releases**: on a `v*` tag, or a manual run with "release" ticked, a final job makes `latest.json` and attaches every installer, signature and `latest.json` to a **draft** release for you to publish.
  - Plain `npm`, `cargo` and `gh` steps rather than `tauri-action`, so the release is made once from all platforms' files (no jobs racing to edit one `latest.json`) and every step can be run by hand.
- Signing switches on per OS when its secrets exist, and is skipped otherwise. Until then: Windows unsigned, macOS ad-hoc signed (D88).

### 2.6 Updater (slice F)

- **Keys** (D91): the public key goes in `plugins.updater.pubkey` (safe to publish), or the repository variable `TAURI_UPDATER_PUBKEY` until it's committed. The private key lives only in your GitHub secret `TAURI_SIGNING_PRIVATE_KEY`, never in the repository or this environment.
- **Builds**: the committed config keeps `createUpdaterArtifacts: false`, so local builds never need the key; the workflow turns it on when the secret exists, and stops if there's a private key but no public one. The app starts the updater only when it has a public key; otherwise Settings says this copy doesn't update itself.
- The endpoint is `https://github.com/mikehuntskankhunt422-dev/Logbook/releases/latest/download/latest.json`, so **publishing** a release is what ships an update.
- `latest.json` is written by `apps/desktop/scripts/latest-json.ts` from the release's `.sig` files (unit-tested). It has an entry per installer (`windows-x86_64-nsis`, `-msi`, `linux-x86_64-appimage`, `-deb`, `-rpm`, `darwin-*-app`) plus the plain `{os}-{arch}` one for the usual installer of each OS.
- The app checks at launch (at most once a day) and from Settings → Updates. It shows "Logbook X.Y is ready to install", and installs and restarts only when you click (D87). Signatures name their version and the app requires it (`requireSignedVersion: true`, D91).
- **Tested on the real app** (`npm run updater:check -w @logbook/desktop`): a throwaway key made in a temporary folder and deleted afterwards; an installed 0.1.0 AppImage driven through WebDriver to find, verify and install a 0.1.1 served from this machine; then a tampered download and an old signature announced as a newer version, both refused (§3 F).

### B. The folder (done)

- **`packages/storage-fs`**: `FsStore` implements `RecordStore` over a five-call `JournalFs` interface (list, read texts, read bytes, write, rename, remove); `NodeJournalFs` (`@logbook/storage-fs/node`) for tests and scripts. It indexes the folder in memory from one listing, writes through a temporary `~lb-….tmp` file renamed into place (D81), and keeps device keys in `LocalKeys` (D80). Ids become file names, so only `[0-9A-Za-z_-]{1,64}` is accepted from files or for writing: a synced file claiming the id `../../escape` is ignored and listed as a problem.
- **Tests (24)**: the shared `RecordStore` contract, plus file names and folders, renames on title, date and trash, media named by type (and renamed once a typeless file's details arrive), device keys kept out of the folder, reopening, passcode on and off (`.json.enc`, `.bin.enc`, nothing readable left), unknown files left alone even by "Delete everything", temporary files cleaned, newer or damaged `logbook.json` refused, settings from an unpacked backup, outside changes (added, edited, removed, half-written then complete, media, a passcode set elsewhere), and conflicts (grouped by id, kept, discarded, renamed on two computers, a version moved aside rather than overwritten, sealed versions decrypted). Removing the old file after a rename was mutated out to check the tests notice: 4 failed.
- **Core**: `Journal.open(store, { mediaGraceDays })` (D84, tested), `readEntryRecord` (decrypts one version for the conflict view), `notifyExternalChange`, `mimeForExtension`.
- **Rust** (`src-tauri/src/folder.rs`): `choose_journal_folder` (native dialog → `journal_root` → grant → remember), `journal_folder`, and the bulk `scan_journal` and `read_journal_texts`, both confined to the folder (no `..`, `.`, empty parts, drive letters or backslashes; symbolic links not followed). 6 Rust tests cover the folder rules and the confinement. `LOGBOOK_JOURNAL_FOLDER` opens a folder without the dialog, for tests. The capability grants the fs commands with **no static scope**.
- **Web**: the desktop boot (`src/desktop/boot.tsx`) opens the remembered folder, or shows "Where should your journal live?", or "Logbook can't open your journal folder" with Try again / Choose another folder. Settings shows "Journal folder" (path, unreadable files, "Use a different folder…") instead of browser storage; backups are saved through the system save dialog; texts that said "this device" or "your browser's files" say "the journal folder" on the desktop.
- **The website's bundle has no desktop code** (checked by grepping the build). The bundler doesn't fold a constant imported from another module, so `IS_DESKTOP` alone left the desktop chunks in the website build (lazy, never loaded, but precached by the service worker); the three places that import desktop code now test `import.meta.env.VITE_PLATFORM` directly.

### C. Sync and conflicts (done)

- `src/desktop/DesktopBar.tsx`, loaded only in the desktop build: on mount, on every debounced folder event (fs plugin `watch`, recursive, 600 ms) and whenever the window regains focus, it calls `FsStore.refresh()`. Views reload only when entries or media really changed (the store compares content, so its own writes don't count).
- **Conflicts**: a banner ("An entry was changed on two computers at once…") opens "Which version should Logbook keep?": every version side by side, decrypted when a passcode is on, with title, date, when it was changed, words, photos, the start of the text and the file name; **Keep this version** on each, **Keep both as separate entries** (the others become new entries titled "… (other version)"), and **Decide later**. A version that can't be decrypted can only be deleted. Nothing is removed until a button is pressed.
- **A passcode set or removed on another computer**: the journal in memory would go on writing with the old key, which could leave entries nobody can open, so the app says so and reopens the journal 2.5 s later (it then shows the lock screen).
- **Tests, real app** (`e2e/sync.test.ts`, WebDriver): an entry written into the folder from outside appears in the timeline in about 0.6 s without a restart; an outside edit shows; a Dropbox-style `… (Laptop's conflicted copy).json` brings up the banner, and keeping version 2 leaves exactly one correctly named file with its content; an OneDrive-style `…-DESKTOP-PC.json` kept as both gives two entries and three files; a vault written into `logbook.json` brings up the notice and then the lock screen. 5 tests, 7 s.

  2. Two AppImages built with it: 0.1.1 as the update, 0.1.0 as the installed app. `latest.json` and the update are served from this machine.
  3. The installed app is driven through WebDriver: Settings → Check for updates → "Logbook 0.1.1 is ready to install" → Install and restart.

  Results:
  - **Installed**: the AppImage on disk became 0.1.1, byte for byte.
  - **A tampered download** (the same file plus 8 bytes) **is refused**: "The update wasn't installed: The signature verification failed", and the installed app is unchanged.
  - **The 0.1.1 signature announced as 0.1.2 is refused**: "The update was signed for version 0.1.1 but the update endpoint announced version 0.1.2…", and the app is unchanged.
- The first run of that check found a real bug: the banner's **Install and restart** hid the banner when the install failed, so the failure vanished. Install errors now stay in the banner with **Dismiss**.
- Until your key exists the workflow builds no update files and releases have no `latest.json` (it says so in the log). Installed apps then aren't offered that release, so **the first release that installed copies can update *from* must be built with the key**.

## 5. Risks specific to M5

| Risk | Mitigation |
|---|---|
| Sync services deliver files out of order or make conflict copies | Conflicts found by id whatever the names; nothing deleted without a choice; media collection waits 7 days (D84); atomic writes |
| Two Logbook windows (or computers) write the same entry at once | Saves check the entry's revision (existing `ConflictError` path); file-level copies go to the conflict view |
| Large journals start slowly over IPC | One Rust call lists the folder and one reads all small files; measured in §3 |
| WebView differences (WebKitGTK on Linux, WKWebView on macOS) break a feature the Chromium e2e tests don't cover | The app is started from its AppImage here; macOS and Windows get CI builds but no automated UI run. First manual run on each OS is in §6 |
| Unsigned installers scare people (SmartScreen, Gatekeeper) | Release notes say how to open them; signing routes in §6 and `docs/SIGNING.md` |
| The updater key is lost | Back it up offline as well as in the GitHub secret (§6); without it no installed app can be updated |
| A GitHub runner image or action changes | Versions pinned; the build runs on every desktop change, not only at release time |
