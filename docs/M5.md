Status: **in progress, 2026-10-10.** The app runs: it keeps the journal in a folder, adds photos, saves backups through a save dialog, and opens Stripe in the browser to pay. A smoke test drives the real app window on Linux in CI, and a workflow builds installers for all three systems. ## 0. In one paragraph

Logbook is a desktop app people download (D78). M5 wraps the journal you already have (the same screens as the browser build) in a Tauri 2 window, keeps the journal as ordinary files in a folder on the computer, and packages it as installers that update themselves. **Done means** that on Windows, macOS and Linux you can install Logbook from a GitHub release, choose a folder (or open one from another computer or an unzipped backup), write entries with photos that land as readable files, order a book (Stripe in the browser, the order followed in the app), and get the next version automatically. A change made in the folder by another computer through OneDrive or Dropbox should show up, and conflict copies should be offered for review.

## 1. What's built

### 1.1 The journal as files (slice A)

`FolderStore` implements the same `RecordStore` contract as the browser's IndexedDB store and passes its shared tests. Its folder uses the backup zip's layout (core `backup.ts`), so an unzipped backup is a working journal:

```
Logbook/
  logbook.json                                      settings, and the vault when a passcode is on
  entries/2026/2026-10-10--desktop-day--5bz1tyhkec5z.json
  trash/2026/…                                      deleted entries (kept 30 days)
  media/4c/4c9e6vddtnrw.png + 4c9e6vddtnrw.meta.json
  entries/<id>.json.enc, media/<xx>/<id>.bin.enc …  the same with a passcode
  .logbook/book-draft.json, book-orders.json        the book builder's state; not part of backups
```

- An entry's file is named by its date and title and moves when either changes, or when it's trashed or restored. Media files take their extension from their details (`.png`), or `.bin.enc` with a passcode. Turning a passcode on or off rewrites every file into the other form.
- Writes are atomic: a temporary file beside the target, flushed, then renamed over it. A crash or a sync tool never sees half a file.
- **Another computer's rename** can briefly leave two files for one entry. Reads take the one with the higher `rev`, and the next save removes the other.
- **Sync conflict copies** ("… (conflicted copy).json" from Dropbox, "…-LAPTOP.json" from OneDrive) don't match the naming scheme. They're never read as entries; `conflicts()` lists them, with the entry they probably belong to, for slice D's review screen.
- A file that isn't valid JSON (a sync still in progress) is skipped and listed by `unreadableFiles()`.
- Tests (`packages/storage-fs/test`, 22): the contract, the layout, renames and trash, reopening, passcode on and off, an unzipped backup opening as a journal, the rename race, conflict copies, unreadable files, a folder with someone else's `logbook.json`, and path safety.

### 1.2 The app (slice B)

- **One web build, two modes.** `vite build --mode desktop` (`npm run build:desktop -w @logbook/web`) leaves out the service worker and web manifest and sets `VITE_PLATFORM=desktop`. Desktop-only code is behind that flag, written inline where it decides whether a chunk exists, so the website bundle carries none of it (checked: no desktop chunk in `dist/` or its service-worker precache).
- **First run** asks where to keep the journal: `Documents/Logbook` (home folder on Linux without a Documents folder), or a folder the person picks. Picking a folder that already holds a journal opens it. Picking one that holds other files makes a `Logbook` folder inside it. The choice is remembered in the app's config file. If the remembered folder is missing at startup (an unplugged drive), the first-run screen says so instead of silently starting a new journal.
- **Settings** shows the folder, with "Show in Explorer/Finder" and "Open a different journal folder…", in place of the browser's storage panel.
- **Files only inside the journal folder.** The Rust side (`src-tauri/src/journal_fs.rs`) resolves every path inside the chosen folder and refuses `..`, absolute paths, drive letters and backslashes, mirroring `assertRelativePath`. No Tauri file-system plugin, so no scope to get wrong. File contents travel as raw bytes, not JSON.
- **What a web page can't do:** backups and attachments go through a save dialog (`save_file`); web links open in the default browser (`open_url`, http, https and mailto only); a second launch focuses the open window rather than starting a second copy on the same folder.
- **Tests:** Rust unit tests (path safety, file operations, folder choice, config, header decoding), `cargo clippy -D warnings`, and `apps/desktop/e2e/smoke.ts`, which drives the built app through WebDriver (tauri-driver and WebKitWebDriver, Linux only) in a fresh home folder.

Smoke test, 2026-10-10 (Ubuntu 24.04, WebKitGTK 2.52.6 under Xvfb), 10 runs, every check passing in each:

```
✓ first run asks where to keep the journal
✓ the journal folder is /tmp/logbook-desktop-e2e-…/Logbook
  files: entries/2026/2026-10-10--desktop-day--5bz1tyhkec5z.json, logbook.json, media/4c/4c9e6vddtnrw.meta.json, media/4c/4c9e6vddtnrw.png
✓ the entry is a readable file named after its date and title
✓ the file holds the title and text
✓ the photo and its details are files in media/
✓ logbook.json holds the settings
✓ a restart opens the remembered folder without asking again
✓ the entry is listed after a restart
✓ Settings shows the journal folder
```

Two things seen while writing it:

- WebKitWebDriver's file upload (sending a path to a file input) ended the session. The test hands the photo to the input the way a drop would; the app's import code is the same from there.
- One run printed `malloc(): unaligned fastbin chunk detected` from a native process, yet passed. It didn't recur in the next 8 runs, with or without the app's output captured separately, so I couldn't tell which process it came from. Most likely WebKit's software rendering under Xvfb (no GPU). Worth watching in CI; if it shows up on real machines, it's a WebKitGTK report.

The browser build is unchanged in behaviour: lint, typecheck, 306 unit tests and the 25 Playwright end-to-end tests (desktop Chromium) pass.

### 1.3 Ordering from the desktop (slice C, D79)

A browser can't bring the app's window back after paying, so:

1. "Continue to payment" asks the API for Stripe's page with `returnUrl` set to the API's own `/api/checkout/done` page, then opens Stripe in the default browser.
2. The app follows the order: every 3 seconds for two minutes, then every 10 seconds until the order is paid or the payment page expires (60 minutes, D56), and at once whenever its window gets focus. The order page says the payment page is open in the browser.
3. After paying (or leaving), Stripe sends the browser to `/api/checkout/done`, a short page saying to go back to Logbook, worded for "paid" or "nothing was charged". It names no order; the order ID stays in the address's `#fragment`, which never reaches the server.

The server accepts that return address only at `PUBLIC_URL` (the API's public address, https in live mode), and lets the app's origins (`tauri://localhost`, `http://tauri.localhost`) call the order API. Unit tests cover the return address, the page, the CORS answer and the config. **Not run end to end yet:** the desktop build needs the API's address (`VITE_API_URL`) baked in, and there's no deployed API until M6. In the dev window (`npm run desktop`), `/api` is proxied to a local server as in the browser.

### 1.4 Installers (slice E, D84)

`.github/workflows/desktop-release.yml` builds the installers on GitHub's Windows, macOS and Ubuntu 22.04 runners. A push to a work branch leaves them as workflow artifacts; a `v*` tag matching the app's version also publishes them as a GitHub release, a pre-release while the version is `0.x`, with `SHA256SUMS.txt` and the notes in `apps/desktop/RELEASE-NOTES.md`. Releasing is described in [DEVELOPING.md](DEVELOPING.md#installers-and-releases).

A desktop build without the API's address (no `LOGBOOK_API_URL` repository variable, as now) can build and preview a book; the "Print files" step says ordering isn't open yet instead of blaming the connection.

Checked here on 2026-10-10 (Ubuntu 24.04): the release build made `Logbook_0.1.0_amd64.AppImage` (82 MB), `Logbook_0.1.0_amd64.deb` (7 MB, depends on `libwebkit2gtk-4.1-0` and `libgtk-3-0`) and `Logbook-0.1.0-1.x86_64.rpm` (7 MB). The smoke test passed against the release binary and against the AppImage itself. The workflow's first run ([run 38036419806](https://github.com/mikehuntskankhunt422-dev/Logbook/actions/runs/38036419806), on this branch) built all three: `Logbook_0.1.0_x64-setup.exe` (6.2 MB), `Logbook_0.1.0_universal.dmg` (13.7 MB), and the three Linux files, in about 7 minutes. Nobody has opened the Windows or macOS installers on a real computer yet.

### 1.5 Pre-merge review (2026-10-10)

Before merging, five reviewers each read one part of the branch (Rust, folder storage, the app's screens, the server, release and docs), and for each part a second reviewer tried to disprove every finding, mostly by reproducing it against the real code. Of 24 findings, 21 held up and 3 didn't. All 21 are fixed:

| Finding (severity) | Fix |
|---|---|
| An unreadable `logbook.json` made the next save drop the passcode's key: every encrypted entry lost for good (high) | Never rewritten; the folder won't open; the key is mirrored in `.logbook/vault.json` (D85) |
| Photo clean-up deleted photos whose entries hadn't synced to this computer yet, on every computer (high) | Off for folder journals (D85) |
| Turning the passcode off on one computer dropped the key while another computer's sealed entry was still arriving (medium) | Re-reads the folder first, refuses while anything stays sealed, keeps the old key (D85) |
| A window left open kept sealing with a key another computer had removed (low) | Unlock re-reads the key; sealing checks it (`VaultChangedError`) |
| A save after another computer renamed the entry overwrote it with no conflict (medium) | A read whose files have gone rescans the folder; same-revision copies are both kept (D85) |
| On macOS 13 and earlier, entries and photos iCloud Drive offloaded vanished from the journal and from backups (medium) | `.<name>.icloud` placeholders are listed under their real names and downloaded on read (`brctl download`) |
| Closing or quitting within a second of typing lost the last edit (low) | The window saves first (D86); the smoke test closes the window as a close button does, and fails with the fix switched off |
| A chosen folder holding only `.DS_Store` or `desktop.ini` got a nested `Logbook` folder (low) | System clutter doesn't count |
| Backups were copied once more in Rust than needed (low) | The request body is borrowed |
| Clicking a link while editing an entry opened the browser (medium) | Links inside text being edited are left alone |
| "Delete everything" said "from this device" but deletes the synced folder everywhere (medium) | Desktop wording says so |
| A folder that couldn't be opened left an error screen with no way out (low) | The folder screen shows the reason and offers another folder |
| Backup and attachment save failures were silent (low) | Shown as messages |
| The order bucket's CORS rules never allowed the desktop app (medium) | `storage:setup` adds the app's origins (or `*` if refused) and checks the app's origin |
| Live mode started without `PUBLIC_URL`, so no desktop customer could pay, with an error about a "website" (medium) | Required in live mode with Stripe; neutral message and a server log |
| The dev window couldn't order through its `/api` proxy (low) | Ordering is on in the dev window |
| Releases kept writing 0.1.0 into backups; the release notes named 0.1.0 files (low) | One version, in `apps/desktop/package.json`; notes without versions |
| macOS first-open steps only fitted macOS 15 (low) | Steps for both |

Not taken up: the browser build still carried a 362-byte desktop chunk it never loads (fixed anyway with inline checks), a docs sentence judged accurate, and `PUBLIC_URL` values that can never match (rejected: they fail loudly at the first checkout).

## 2. Still to do

- **D. Watching the folder.** A file watcher (Rust `notify`) tells the app when files change outside it; the store rescans and the open screens reload, unless the change is the app's own write. Conflict copies and unreadable files get a review screen: open both versions side by side, keep one, or keep both as separate entries.
- **F. Automatic updates.** Tauri's updater plugin checks `latest.json` on the latest GitHub release and installs updates signed with our own updater key (free, unrelated to OS code signing). The public key goes in the app; the private key must live only in a repository secret.
- **G. Content Security Policy** for the desktop window (D82).
- **Large videos** are read whole into memory to play. Fine for photos and short clips; long videos should stream through Tauri's asset protocol instead.

## 3. Running it

```bash
npm run desktop               # dev window with hot reload (Vite on :5174; `npm run dev -w @logbook/server` for /api)
npm run desktop:build         # installers for this OS in apps/desktop/src-tauri/target/release/bundle/
```

On Linux, Tauri needs `libwebkit2gtk-4.1-dev libxdo-dev libssl-dev libayatana-appindicator3-dev librsvg2-dev`; Windows and macOS need only Rust and their build tools. The smoke test: `npx tauri build --debug --no-bundle` in `apps/desktop`, then `xvfb-run -a npm run test:e2e -w @logbook/desktop` (needs `cargo install tauri-driver --version =2.0.6 --locked` and `webkit2gtk-driver`).
