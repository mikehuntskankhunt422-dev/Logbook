# Milestone 5: The desktop app

Status: **in progress, 2026-10-10.** The app runs: it keeps the journal in a folder, adds photos, saves backups through a save dialog, and opens Stripe in the browser to pay. A smoke test drives the real app window on Linux in CI, and a workflow builds installers for all three systems. Automatic updates are built (slice F, 2026-10-11, §1.6), and changes made by another computer show up, with sync copies to sort out (slice D, 2026-10-24, §1.9); and the window has a security policy (slice G, 2026-10-26, §1.10) · Expands [PLAN.md](PLAN.md) §1.1–1.2, §2 and §3 (M5), for a desktop-only Logbook (D77, D78) · Author: Claude

## 0. In one paragraph

Logbook is a desktop app people download (D78). M5 wraps the journal you already have (the same screens as the browser build) in a Tauri 2 window, keeps the journal as ordinary files in a folder on the computer, and packages it as installers that update themselves. **Done means** that on Windows, macOS and Linux you can install Logbook from a GitHub release, choose a folder (or open one from another computer or an unzipped backup), write entries with photos that land as readable files, order a book (Stripe in the browser, the order followed in the app), and get the next version automatically. A change made in the folder by another computer through OneDrive or Dropbox should show up, and conflict copies should be offered for review.

## 1. What's built

### 1.1 The journal as files (slice A)

`FolderStore` implements the same `RecordStore` contract as the browser's IndexedDB store and passes its shared tests. Its folder uses the backup zip's layout (core `backup.ts`), so an unzipped backup is a working journal:

```
Logbook/
  logbook.json                                      settings, and the vault when a passcode is on
  entries/2026/2026-10-10--desktop-day--5bz1tyhkec5z.json
  trash/2026/…                                      deleted entries (kept 30 days)
  media/4c/4c9e6vddtnrw.png + 4c9e6vddtnrw.meta.json
  entries/<id>.json.enc, media/<xx>/<id>.bin.enc …  the same with a passcode
  .logbook/book-draft.json, book-orders.json        the book builder's state; not part of backups
```

- An entry's file is named by its date and title and moves when either changes, or when it's trashed or restored. Media files take their extension from their details (`.png`), or `.bin.enc` with a passcode. Turning a passcode on or off rewrites every file into the other form.
- Writes are atomic: a temporary file beside the target, flushed, then renamed over it. A crash or a sync tool never sees half a file.
- **Another computer's rename** can briefly leave two files for one entry. Reads take the one with the higher `rev`, and the next save removes the other.
- **Sync conflict copies** ("… (conflicted copy).json" from Dropbox, "…-LAPTOP.json" from OneDrive) don't match the naming scheme. They're never read as entries; `conflicts()` lists them, with the entry they probably belong to, for slice D's review screen (§1.9).
- A file that isn't valid JSON (a sync still in progress) is skipped and listed by `unreadableFiles()`.
- Tests (`packages/storage-fs/test`, 22): the contract, the layout, renames and trash, reopening, passcode on and off, an unzipped backup opening as a journal, the rename race, conflict copies, unreadable files, a folder with someone else's `logbook.json`, and path safety.

### 1.2 The app (slice B)

- **One web build, two modes.** `vite build --mode desktop` (`npm run build:desktop -w @logbook/web`) leaves out the service worker and web manifest and sets `VITE_PLATFORM=desktop`. Desktop-only code is behind that flag, written inline where it decides whether a chunk exists, so the website bundle carries none of it (checked: no desktop chunk in `dist/` or its service-worker precache).
- **First run** asks where to keep the journal: `Documents/Logbook` (home folder on Linux without a Documents folder), or a folder the person picks. Picking a folder that already holds a journal opens it. Picking one that holds other files makes a `Logbook` folder inside it. The choice is remembered in the app's config file. If the remembered folder is missing at startup (an unplugged drive), the first-run screen says so instead of silently starting a new journal.
- **Settings** shows the folder, with "Show in Explorer/Finder" and "Open a different journal folder…", in place of the browser's storage panel.
- **Files only inside the journal folder.** The Rust side (`src-tauri/src/journal_fs.rs`) resolves every path inside the chosen folder and refuses `..`, absolute paths, drive letters and backslashes, mirroring `assertRelativePath`. No Tauri file-system plugin, so no scope to get wrong. File contents travel as raw bytes, not JSON.
- **What a web page can't do:** backups and attachments go through a save dialog (`save_file`); web links open in the default browser (`open_url`, http, https and mailto only); a second launch focuses the open window rather than starting a second copy on the same folder.
- **Tests:** Rust unit tests (path safety, file operations, folder choice, config, header decoding), `cargo clippy -D warnings`, and `apps/desktop/e2e/smoke.ts`, which drives the built app through WebDriver (tauri-driver and WebKitWebDriver, Linux only) in a fresh home folder.

Smoke test, 2026-10-10 (Ubuntu 24.04, WebKitGTK 2.52.6 under Xvfb), 10 runs, every check passing in each:

```
✓ first run asks where to keep the journal
✓ the journal folder is /tmp/logbook-desktop-e2e-…/Logbook
  files: entries/2026/2026-10-10--desktop-day--5bz1tyhkec5z.json, logbook.json, media/4c/4c9e6vddtnrw.meta.json, media/4c/4c9e6vddtnrw.png
✓ the entry is a readable file named after its date and title
✓ the file holds the title and text
✓ the photo and its details are files in media/
✓ logbook.json holds the settings
✓ a restart opens the remembered folder without asking again
✓ the entry is listed after a restart
✓ Settings shows the journal folder
```

- One run printed `malloc(): unaligned fastbin chunk detected` from a native process, yet passed. Worth watching in CI; if it shows up on real machines, it's a WebKitGTK report.

The browser build is unchanged in behaviour: lint, typecheck, 306 unit tests and the 25 Playwright end-to-end tests (desktop Chromium) pass.

### 1.3 Ordering from the desktop (slice C, D79)

A browser can't bring the app's window back after paying, so:

1. "Continue to payment" asks the API for Stripe's page with `returnUrl` set to the API's own `/api/checkout/done` page, then opens Stripe in the default browser.
2. The app follows the order: every 3 seconds for two minutes, then every 10 seconds until the order is paid or the payment page expires (60 minutes, D56), and at once whenever its window gets focus. The order page says the payment page is open in the browser.
3. After paying (or leaving), Stripe sends the browser to `/api/checkout/done`, a short page saying to go back to Logbook, worded for "paid" or "nothing was charged". It names no order; the order ID stays in the address's `#fragment`, which never reaches the server.

The server accepts that return address only at `PUBLIC_URL` (the API's public address, https in live mode), and lets the app's origins (`tauri://localhost`, `http://tauri.localhost`) call the order API. Unit tests cover the return address, the page, the CORS answer and the config. **Not run end to end yet:** the desktop build needs the API's address (`VITE_API_URL`) baked in, and there's no deployed API until M6. In the dev window (`npm run desktop`), `/api` is proxied to a local server as in the browser.

Of 24 findings, 21 held up and 3 didn't. All 21 are fixed:

**A second review of the fixes** (three reviewers over the commits above) found that some fixes were themselves incomplete, and those are fixed too, each with a test:

| Finding (severity) | Fix |
|---|---|
| A window that missed another computer turning the passcode on could turn its own on and overwrite that key, or keep writing plain text into the encrypted journal (high) | Every write checks the stored key first; so do turning a passcode on and changing it; a replaced key is always kept (D85) |
| Turning the passcode off could refuse after already writing everything in plain text, refuse forever because of a file sealed with another key, or miss a photo still syncing (medium) | It reads everything first and changes nothing if a file can't be read yet; a file this key can't open doesn't stop it (D85) |
| A stale key copy could bring back a passcode that was turned off (medium) | The copy is used only when `logbook.json` is missing, and is set aside before `logbook.json` is rewritten |
| The kept conflict copy was indexed again after a restart and deleted by the next save; with a passcode turned on meanwhile it could even replace the person's version (medium) | Kept as `… (conflict …).json`, outside the naming scheme |
| "Delete forever" and the 30-day trash purge stopped deleting the entries' photos (medium) | They delete what those entries used, after re-reading the folder |

**A final review** (three reviewers, each with a skeptic, over those fixes and over the server and docs) confirmed 13 more findings and rejected 3. All 13 are fixed: changing the passcode no longer leaves the old passcode able to open the journal (every key that's *replaced* is kept, one file each in `.logbook/previous-vaults/`); a photo sealed with another key no longer blocks turning the passcode off, listing photos or a plain backup; turning the passcode off waits while a photo's data is still syncing; backups refuse rather than silently leave out a file that can't be read; a kept conflict copy is moved aside before a save lands on its name, and a sealed and a plain copy of one entry are both kept; a close whose last save failed is called off (closing again within 15 s goes ahead); opening Logbook again while it closes keeps the window; iCloud stops waiting only after two different files time out; and these docs. The close-after-a-failed-save path has no automated test yet.

### 1.6 Automatic updates (slice F, D88)

- **Rust** (`src-tauri/src/lib.rs`): `tauri-plugin-updater` 2.13.1 behind two commands. `update_check` reads `latest.json` from `https://github.com/mikehuntskankhunt422-dev/Logbook/releases/latest/download/` and keeps what it found; `update_install` downloads it, checks its signature against the public key in `tauri.conf.json`, installs it, reports progress (`logbook://update-progress`) and restarts. On Windows the NSIS installer runs in passive mode (a progress bar, no questions) and starts Logbook again itself.
- **The page** (`apps/web/src/desktop/updates.ts`, `UpdatesPanel.tsx`): a quiet check 10 s after starting and every 12 hours, which offers a new version in a toast (**Update and restart**); **Settings → Updates** shows the version, a **Check for updates** button, progress and any error. Before installing, everything is saved (`saving.ts`, shared with closing, D86); if the last writing can't be saved, the update waits.
- **Releases** (`desktop-release.yml`): with the key in the repository secrets, `tauri build` also makes the signed update files (`--config src-tauri/tauri.release.conf.json`): `.sig` for the NSIS setup, the AppImage, the deb and the rpm, and `Logbook.app.tar.gz` with its `.sig` on macOS. `apps/desktop/scripts/latest-json.ts` writes `latest.json` and refuses if a file or signature is missing, or if a signature doesn't verify against the public key in `tauri.conf.json` (a private key that isn't its other half would otherwise ship updates every installed copy rejects). Each build also checks its own files that way (`--verify`), so a wrong secret shows up on any branch, not only at release. Releases are no longer GitHub pre-releases, so `releases/latest` finds them. Publishing fails without the key; branch builds don't need it.
- **Tested here (2026-10-11, Ubuntu 24.04, throwaway key):** a debug AppImage of 0.1.0 with a test key and a local `latest.json`, and a signed 0.1.1 (AppImage, deb and rpm each got their `.sig`), driven through WebDriver: the check 10 s after starting offered 0.1.1 in a toast; Settings → Updates showed "You have Logbook 0.1.0" and the offer; with one character of the signature changed, **Update and restart** downloaded the file and refused it ("The signature verification failed"), leaving the AppImage as it was; **Try again** looked again, got the correct file, replaced the AppImage with 0.1.1 byte for byte, and Logbook started again from it. The desktop smoke test (13 checks, including saving before closing, which now shares its code with updating) and the 327 unit tests pass.
- **Not tested:** Windows and macOS updating themselves (the same plugin and our same commands, but no machine here); a real GitHub release, which happens with 0.2.0. Copies of 0.1.0 have no updater: people on it download 0.2.0 once by hand.

### 1.8 Pre-merge review of updates and export (2026-10-11)

Three reviewers (the updater and release workflow; the export converters; the export screen and printing), each followed by a skeptic who tried to refute every finding, as in §1.5. 15 findings held up and 4 were rejected (a name-length limit only reachable with 58+ four-byte characters, NFC/NFD twins of one name, link blocks in print showing no address, which D89 intends, and full-size photos in the print layout, which the engines' decode caches handle). All 15 are fixed:

| Finding | Fix |
|---|---|
| The real updater key and password were in the environment of every branch build, so any dependency or build script could read them (medium) | Builds sign with a throwaway key; only a release re-signs, in a step that runs a fresh copy of Tauri's CLI outside the checkout (D88). The build job reads the repository with `contents: read` and leaves no git credentials behind |
| A PDF still being prepared when the journal locked opened the print window over the lock screen, with the decrypted entries left in the page (medium) | It stops on a lock, or when Settings closes; a lock removes the print layout at once; a lock during a file export saves nothing |
| Exports held about three copies of their media in memory, and a zip over 4 GB came out corrupt (medium) | The zip is streamed as backups are; over 4 GB is refused with a clear message |
| Writing done while an update downloaded could be lost when it installed (low) | Download, then block the window, save again, then install |
| The update offer went nowhere on the folder and error screens, including "Update the app first" (low) | Those screens show it |
| An auto-lock during an export left nameless "File" placeholders and blamed syncing (low) | It stops with a message about the lock; media without a record is named by its block ("Photo") |
| Linux can still be printing after its dialog closes, so leaving Settings could blank pages (low) | The layout stays a minute after Settings closes (a lock still removes it at once) |
| Markdown: a closing `#` lost from headings; captions with spaces turning into list items; `javascript:` link blocks written as links; paragraphs in one list item merging; emphasis next to punctuation (and in Chinese and Japanese) shown as asterisks; stray backslashes from line breaks (low) | Each fixed, with unit tests; 24 cases also checked by rendering with markdown-it |
| The panel promised a .zip for exports that come out as one file (low) | The hint says what will actually be made |

**A second round** (the same three areas, each with a skeptic) checked those fixes. It confirmed 15 findings and rejected 1. Six were in the release workflow, and all six are fixed by moving the real key into a release-only `sign` job:
- branch builds were still sent the secrets, because GitHub delivers any secret a job's steps mention;
- on a release, the key reached a step that ran after dependency code, on the same machine;
- `npx` could run a copy of Tauri's CLI planted in the restored npm cache;
- re-signing dropped the version bound into each signature;
- the GitHub Environment advice in DEVELOPING.md didn't match the workflow;
- Git Bash on Windows could garble a password that looks like a path.

The other nine are fixed too:
- **Update while editing:** a tag typed during the download was lost when blocking the window took the focus away. Fixed with a pause before the last save.
- **Open dialogs:** a dialog already open stayed usable above the cover. The cover is now a modal dialog itself.
- **Work in progress:** photos being added, a restore or a passcode change could be cut off by the restart. The update now waits for them.
- **Memory:** the zip still held two copies while being built. It now holds one, and the 4 GB check runs before any media is read.
- **Closing Settings:** this didn't stop a file export. It does now.
- **Locking during the save dialog:** the export was still written. Saving now asks again after the dialog and before each piece.
- **Markdown:** a non-web link block could turn into a heading or list, and some sub-lists merged into their paragraph.
- **Printing:** for a minute after leaving Settings, printing another page printed the old export.

The rejected one was closing the window during an AppImage install. That race existed before these changes, and its window is a single file write of well under a second (18–300 ms measured for 82 MB); deb, rpm, macOS and Windows installs don't have it.

Checked after the second round, here: 353 unit tests and 45 browser tests pass. On Linux, the desktop smoke test, the update test (with the modal cover), the PDF print test, and a save of a backup and an export through the real GTK save dialog all pass; the files were complete, with no temporary files left.

### 1.9 Watching the folder (slice D, D102, 2026-10-24)

- **Rust** (`src-tauri/src/watch.rs`): `journal_watch` starts a recursive `notify` watcher on the open folder (again after a switch; the same folder is a no-op). Events pass `news()`: reads and metadata changes, `.logbook-tmp-` files, the write test, clutter (`folder::is_clutter`, now with Office's `~$` lock files) and paths `journal_fs` wrote, renamed or removed in the last 5 s are left out; an overflowed queue sends `*`. `settle()` batches them: 0.6 s of quiet, or 3 s after the first. Three Rust tests.
- **Core** (`packages/core/src/journal.ts`): `refresh()` (the store rescans, settings are reparsed and announced if they changed, then `entries` and `media`), `entryCopies()`, `settleCopy(path, 'ours' | 'theirs' | 'both')`, `deleteCopy(path)` and `keepVersion(entry)`. `FolderStore` gains `readCopy`, `removeCopy` and `keepCopy`; a same-rev copy it moved aside (`keepAside`) is followed by its old path.
- **The page**: `desktop/sync.ts` (the listener, one refresh at a time; the banner's count), `desktop/CopiesView.tsx` (`#/copies` and the banner), and `EntryEditor.tsx` (an untouched open entry follows the store; on a `ConflictError`, the person's version is kept with `keepVersion` and a toast offers **Compare** or **Open it**).
- **Reviewed** (data safety, the watching plumbing, the page; 2026-10-24) and hardened: saves and refreshes take turns, kept same-rev copies survive a rescan, a version saved elsewhere with the same revision is a conflict, the copies page won't replace an entry whose own file it can't read, settings changed here aren't read over, a passcode changed elsewhere locks the journal, and Logbook's own folders, finished big writes and OneDrive's upload marks aren't news (D102).
- **Reviewed again** (the fixes, 2026-10-26): a kept copy saved over by another computer, a refresh during a passcode change, and a journal folder that goes away are now handled (D102).
- **Tested here (Linux):** 20 unit tests, 6 Rust tests and seven new checks in the desktop smoke test pass (an entry written from outside appears without a restart; an open entry shows another computer's rename; a Dropbox-style copy brings the banner, is shown beside its entry, passes axe, and is kept as an entry of its own; deleting an open entry says nothing about another computer); the 56 browser tests pass. **Not tested:** Windows and macOS watching a real Dropbox or OneDrive folder (the same `notify` crate, ReadDirectoryChangesW and FSEvents; both compile in `desktop-release.yml`). **Known gaps:** Windows doesn't report a dropped batch of changes (they arrive at the next refresh: the next change, or coming back after a minute away); changes made between opening the journal and the watch starting (about a second) wait for the same.

### 1.10 The window's security policy (slice G, D104, 2026-10-26)

- **What:** a Content Security Policy for the app's window on the desktop and Android (`src-tauri/tauri.conf.json`; `tauri.macos.conf.json` adds `'unsafe-eval'` for macOS 10.15's older engine): only Logbook's own scripts run, WebAssembly is allowed for the passcode, and the page reaches only Tauri's commands, Rumble's oEmbed and the seven video players music links and embeds use. The page records anything blocked (`desktop/boot.tsx`).
- **Tested here (Linux):** the smoke test's 36 checks pass, with five new ones: nothing blocked on a first run or through the icon, sync, copies and a video player; WebAssembly compiles; a script slipped into the page doesn't run or send anything; and the console says what was blocked. The Android emulator test gains two checks (nothing blocked; WebAssembly compiles, which Chromium refuses without `'wasm-unsafe-eval'`). **Not tested:** Windows and macOS windows (same policy; Windows' WebView2 behaves like Android's Chromium).

## 3. Running it

```bash
npm run desktop               # dev window with hot reload (Vite on :5174; `npm run dev -w @logbook/server` for /api)
npm run desktop:build         # installers for this OS in apps/desktop/src-tauri/target/release/bundle/
```

On Linux, Tauri needs `libwebkit2gtk-4.1-dev libxdo-dev libssl-dev libayatana-appindicator3-dev librsvg2-dev`; Windows and macOS need only Rust and their build tools.
